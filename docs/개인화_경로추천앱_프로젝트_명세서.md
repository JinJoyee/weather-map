# 🗺️ 개인화 경로 추천 앱 — 프로젝트 명세서

## 1. 프로젝트 개요

### 핵심 컨셉
> 기존 지도 앱이 제공하지 못하는 **날씨·시간대(자외선/야간) 기반의 상황 인식 경로 추천** +
> **사용자 커스텀 경로 등록** 기능에 집중한 경로 추천 서비스

### 차별화 포인트 (발표 방어용 핵심)

| 기존 서비스 | 우리 서비스 |
|---|---|
| 최단거리/최소시간 단일 기준 | **상황(날씨·시간대)에 따라 다른 경로 자동 전환** |
| 날씨 정보는 단순 표시용 | **날씨가 경로 선택 로직에 직접 관여** (비→지하경로, 폭염→그늘경로) |
| 자외선/야간 정보 없음 | **자외선 지수 높으면 그늘·실내 경로, 야간이면 안전(조명) 경로** |
| 경로 커스터마이징 불가 | **사용자가 직접 경로를 그려서 등록·공유 가능** |

> **중간발표 방어 핵심**: "우리는 지도 앱 전체를 만드는 것이 아니라, **기존 지도 API 위에 '상황 인식 경로 전환'이라는 특정 레이어**를 얹는 것이다."

## 2. 기능 범위 (MVP 기준)

### ✅ 구현할 것 (In-Scope)

| 기능 | 설명 | 우선순위 |
|---|---|---|
| **날씨 기반 경로 전환** | 비/눈 → 지하·실내 경유 경로 추천 | 🔴 필수 |
| **시간대 기반 경로 전환** | 야간 → 조명 밝은 도로 중심 경로 | 🔴 필수 |
| **자외선 지수 기반 경로** | UV 높음 → 그늘·건물 그림자 경로 | 🔴 필수 |
| **커스텀 경로 등록** | 사용자가 지도에 직접 경로를 그려서 저장 | 🟡 중요 |
| **경로 비교 화면** | 일반 경로 vs 상황 인식 경로 비교 UI | 🟡 중요 |
| **커스텀 경로 공유** | 등록한 경로를 다른 사용자에게 공유 | 🟢 선택 |

### ❌ 구현하지 않을 것 (Out-of-Scope)

- 실시간 내비게이션 (턴바이턴 안내)
- 대중교통 실시간 도착 정보
- 자체 지도 렌더링 엔진
- 교통량 예측 AI 모델

## 5. 핵심 알고리즘 — 상황 인식 경로 전환 로직

이 부분이 프로젝트의 **기술적 핵심**이자 **차별화 포인트**입니다.

### 5-1. 상황 판단 흐름

```
사용자가 경로 요청
    │
    ▼
┌─────────────────────┐
│  현재 상황 수집       │
│  - 현재 시각          │
│  - 날씨 (기상청 API)  │
│  - 자외선 지수        │
│  - 일몰/일출 시각     │
└─────────┬───────────┘
          │
          ▼
┌─────────────────────────────┐
│  상황 태그 부여              │
│  예: ["야간", "비"]          │
│  예: ["주간", "자외선_높음"] │
└─────────┬───────────────────┘
          │
          ▼
┌─────────────────────────────────┐
│  태그별 경로 가중치 조정         │
│  "야간" → 조명 밝은 도로 가중치↑ │
│  "비"   → 지하/실내 경유 가중치↑ │
│  "UV높음"→ 그늘 경로 가중치↑    │
└─────────┬───────────────────────┘
          │
          ▼
  경로 후보 생성 및 정렬 → 사용자에게 추천
```

### 5-2. 상황 태그 판단 기준

```python
# 예시 코드 (Python)
def get_context_tags(weather_data, uv_index, current_time, sunset, sunrise):
    tags = []

    # 시간대 판단
    if current_time < sunrise or current_time > sunset:
        tags.append("야간")
    else:
        tags.append("주간")

    # 날씨 판단
    if weather_data["rain_probability"] >= 60:
        tags.append("비")
    if weather_data["snow_probability"] >= 60:
        tags.append("눈")

    # 자외선 판단 (주간에만)
    if "주간" in tags and uv_index >= 8:
        tags.append("자외선_매우높음")
    elif "주간" in tags and uv_index >= 6:
        tags.append("자외선_높음")

    return tags
```

### 5-3. 경로 가중치 매핑

| 상황 태그 | 경로 선호 변경 | 구현 방식 |
|---|---|---|
| `야간` | 큰 도로, 조명 있는 길 우선 | Kakao 경로 옵션 중 '큰길 우선' + 안전 POI 경유 |
| `비` / `눈` | 지하도, 아케이드, 실내 통로 경유 | 사전 등록된 실내 경유 포인트(waypoint) 추가 |
| `자외선_높음` | 건물 그늘, 가로수길 우선 | 사전 등록된 그늘 경로 구간 데이터 활용 |
| `자외선_매우높음` | 실내 경로 적극 추천 | 지하상가, 연결통로 waypoint 추가 |

> **구현 핵심**: 자체 경로 알고리즘을 만드는 게 아니라,
> **Kakao Maps 경로 API에 조건별 waypoint를 동적으로 추가**하는 방식으로 구현합니다.

## 6. 데이터베이스 설계 (ERD 개요)

### 주요 테이블

```sql
-- 사용자
CREATE TABLE users (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    email       TEXT UNIQUE NOT NULL,
    nickname    TEXT NOT NULL,
    password    TEXT NOT NULL,  -- bcrypt 해시
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 커스텀 경로
CREATE TABLE custom_routes (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER REFERENCES users(id),
    name        TEXT NOT NULL,           -- "출근길 A코스"
    start_lat   REAL NOT NULL,
    start_lng   REAL NOT NULL,
    end_lat     REAL NOT NULL,
    end_lng     REAL NOT NULL,
    waypoints   TEXT,                    -- JSON: [{lat, lng, label}, ...]
    context_tag TEXT,                    -- "야간" / "비" / "자외선" / "기본"
    is_public   BOOLEAN DEFAULT FALSE,   -- 공유 여부
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 경유 포인트 마스터 (그늘길, 지하도 등)
CREATE TABLE context_waypoints (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    lat         REAL NOT NULL,
    lng         REAL NOT NULL,
    label       TEXT,                    -- "청주 지하상가 입구"
    type        TEXT NOT NULL,           -- "shelter" / "shade" / "lit_road"
    area_code   TEXT                     -- 지역 코드
);

-- 경로 이용 로그 (선택: 분석용)
CREATE TABLE route_logs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER REFERENCES users(id),
    route_id    INTEGER,
    context_tags TEXT,                   -- JSON: ["야간", "비"]
    used_at     DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 9. 개발 가이드라인

### 9-1. Git 컨벤션

**브랜치 전략: GitHub Flow (main + feature_\*)**

```
main                            ← 항상 동작 가능한 상태 유지
├── feature_map_ui              ← 기능 개발
├── feature_weather_api         ← 기능 개발
├── feature_custom_route        ← 기능 개발
├── feature_fix_route_night_bug ← 버그 수정 (feature_fix_* 형태)
└── feature_docs_api_spec       ← 문서 작업 (feature_docs_* 형태)
```

**규칙:**
- **모든 브랜치 이름은 반드시 `feature_`로 시작한다.** (교수님 요구사항 + 팀 합의)
  - 버그 수정·문서·리팩토링도 모두 `feature_` 접두사 유지
  - 세부 분류는 접두사 뒤 단어로 표현: `feature_fix_*`, `feature_docs_*`, `feature_refactor_*`, `feature_chore_*`
- 단어 구분은 **언더스코어(snake_case)**로 통일한다.
  - 예: `feature_weather_api` (○) / `feature/weather-api` (×) / `future_Design` (×) / `feature_날씨연동` (×)
- `dev` 브랜치는 사용하지 않는다. 모든 작업 브랜치는 `main`에서 분기하고 `main`으로 PR한다.
- PR은 최소 1명 리뷰 후 머지하며, 머지 후 원격 브랜치는 삭제한다.
- `main`에는 직접 push하지 않는다. (GitHub branch protection 권장)

**왜 GitFlow가 아니라 GitHub Flow인가?**
- 4인 8주 프로젝트에는 release/hotfix 브랜치 분리가 불필요하다 (배포 버전 관리 대상이 없음).
- `dev` 단계가 추가되면 PR을 두 번(`feature → dev`, `dev → main`) 만들어야 해서 리뷰 비용만 증가한다.
- 단순한 흐름이 4인 협업에서 충돌·머지 실수를 줄인다.

**커밋 메시지 규칙:**
```
feat: 날씨 API 연동 추가
fix: 야간 판단 로직 시간대 오류 수정
docs: API 명세서 업데이트
style: 경로 비교 화면 레이아웃 수정
chore: 패키지 잠금 파일 업데이트
refactor: 경로 추천 함수 분리
```

## 10. 중간발표 예상 질문 & 방어 전략

### Q1. "이거 카카오맵에 있는 기능 아닌가요?"
> **A:** 카카오맵은 날씨와 자외선 지수를 경로 선택 기준에 반영하지 않습니다.
> 저희는 날씨·UV·시간대를 실시간으로 판단해서 경로 자체를 바꿔주는 것이 차별점입니다.
> 기존 앱에서 비가 와도 같은 경로를 추천하는 것과 달리, 저희는 자동으로 지하 경유 경로로 전환합니다.

### Q2. "기술적으로 너무 단순한 것 아닌가요?"
> **A:** 저희 프로젝트의 목표는 복잡한 자체 경로 알고리즘 개발이 아니라,
> 기존 지도 API를 활용하되 **상황 인식이라는 레이어를 추가**하는 것입니다.
> 상황 판단 → 태그 부여 → 조건별 waypoint 동적 생성 → 경로 API 호출의
> 파이프라인을 설계하고 구현하는 것이 기술적 핵심입니다.

### Q3. "그늘길 데이터는 어디서 가져오나요?"
> **A:** MVP 단계에서는 프로젝트 대상 지역(예: 청주 시내, 학교 주변)의
> 그늘길·지하도·아케이드를 직접 조사하여 DB에 수동 등록합니다.
> 이후 사용자 커스텀 경로 등록을 통해 크라우드소싱 방식으로 확장할 수 있습니다.

### Q4. "4명이서 8주 안에 가능한가요?"
> **A:** 자체 지도 엔진이나 내비게이션을 만드는 것이 아니라,
> Kakao Maps API라는 기존 인프라 위에 저희 로직만 얹는 구조이므로
> 프론트 2명, 백엔드 2명으로 충분히 가능합니다.

## 11. 필수 설치 및 세팅 가이드

### 프론트엔드 초기 세팅
```bash
# Node.js 18+ 필요
npm create vite@latest frontend -- --template react
cd frontend
npm install

```

### 백엔드 초기 세팅
```bash
# Python 3.10+ 필요
python -m venv venv
source venv/bin/activate  # Windows: venv\Scripts\activate

pip install fastapi uvicorn sqlalchemy python-jose[cryptography]
pip install httpx python-dotenv bcrypt
```

### 실행
```bash
# 백엔드 실행
cd backend
uvicorn app.main:app --reload --port 8000

# 프론트엔드 실행
cd frontend
npm run dev
```
